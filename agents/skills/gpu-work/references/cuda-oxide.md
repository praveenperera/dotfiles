# cuda-oxide watch-outs

Traps that cost correctness or speed in cuda-oxide kernels, and the checks that catch them. Add to it after each run: one line per trap with the fix, plus the commit it was seen at, since some are bugs that later commits may fix. Recheck old entries when you move to a newer cuda-oxide. Evidence for each entry is in the run logs under `~/code/research/gpu-kernels/cuda-kernels/`. A slowdown you measured but couldn't explain goes under "Open slowdowns" with its suspects, until a test confirms a trap or clears it.

## Coverage

The entries come from one codebase (sam3rs, about 50 kernels: elementwise, norms, convs, flash attention on BF16 and TF32 tensor cores), found at cuda-oxide `2d47e43` on one GPU (RTX 5090, sm_120). Every entry was rechecked with a standalone repro at `88e52d117` (2026-10-31; `cuda-oxide-gotcha-validation-2026-10-31.md`, repros in `~/code/private-workbench/ops/cuda-rust/sam3rs-gotchas/`). The sm_80 tier was checked in SASS only, never run on Ampere. Not yet exercised, so expect unlisted traps there: atomics, grid-wide reductions and cooperative launches, TMA and `wgmma` (sm_90+), FP8, thread-block clusters.

## Setup

- Use a project-owned `CARGO_HOME` for cargo-oxide: the backend cache in `$CARGO_HOME/cuda-oxide/` has one slot, rebuilt whenever a project's `cuda-device` dependency resolves to another commit (`source-rev.txt`).
- Pin the commit in the kernel crate's `Cargo.lock`; the backend is built from that dependency checkout. Install cargo-oxide at the same commit so the CLI matches too. The toolchain is whatever that commit's `rust-toolchain.toml` pins.
- `cargo oxide build` builds the backend when its cache is missing or stale, so a build script needn't call `cargo oxide setup`. In a standalone crate, `setup` builds your crate instead of the backend and exits nonzero ("Cargo reported no librustc_codegen_cuda.so artifact", or "no library targets found"), though the cache `build` made is fine (upstream #1688). `build` recompiles the crate and rewrites the PTX every run when its root is `src/lib.rs` or `src/main.rs`; with another root, check the PTX timestamp.
- Use the toolchain's own llc (LLVM 23.1.1 at `88e52d117`), the default. With `CUDA_OXIDE_LLC=llc-21`, several traps below appear that LLVM 23 doesn't have, and `flash_attn_rpb_d32` is 6% slower.
- The PTX ISA `.version` sets the minimum driver; check it in the build script (7.0 for sm_80, 8.7 for sm_120, with LLVM 21 and 23).

## Speed traps

- **A generic `#[device]` fn drops `#[inline(always)]`** (`88e52d117`, upstream #1471, fix PR #1472 open): LLVM decides by size, so a large body stays a `.func` and its pointers arrive generic (generic `LD` instead of `LDS`/`LDG`: +26% in a repro; `flash_combine_d32` +72% in sam3rs until inlined). Write generic bodies as plain `#[inline(always)]` fns, and unroll their loops with `cuda_device::thread::__unroll_config::<0>()` as the loop body's first statement (0 = fully, N = by N). That marker is the undocumented call `#[unroll]` expands to, so recheck it after every cuda-oxide upgrade (the build's no-`call` check and a SASS look catch a break).
- **mir-lower places some allocas outside the entry block** (`88e52d117`, upstream #1687 and #1681): LLVM treats them as dynamic, so it won't inline the function and SROA leaves them on the stack. It's the cause of the two entries below. If a `.func` or a frame appears with no obvious reason, check the IR for an `alloca` outside `entry:`.
  - **`core::iter::Zip` over a slice iterator and a view iterator** isn't inlined: a `call` and a 72-byte stack, 3.5x slower than a counted loop. Use a counted loop over views. `zip_exact` is fine on LLVM 23 but stays rolled with llc-21 (2.1x slower).
  - **An inline helper returning `Option<(struct, views...)>`** puts the payload on the stack (a 304-byte frame with `LDL`/`STL` in every sam3rs flash kernel that called it; 312 bytes and 3.3x slower in a repro; upstream #1590, whose fix PR #1591 doesn't cover this size). Return a plain tuple and `unreachable_unchecked()` past the one up-front check.
- **64-bit index math** (`i64` indices, as ported from `long long`) compiles `/` and `%` to ptxas's 64-bit divide sequence (nvcc's is no better). 32-bit coordinates (`thread::index_1d_u32`, `element_thread32`, `#[launch_contract(coordinates = u32)]`) divide inline: 20-70% fewer instructions in elementwise and conv kernels, though memory-bound kernels time the same.
- **`f32::max`/`min` become compare + select** (`88e52d117`, upstream #1594, fix PR #1668 open), not one `max.f32`: use libdevice `__nv_fmaxf`/`__nv_fminf` (`math::fmaxf`). `warp::reduce_max_f32`/`reduce_min_f32` use them too (`warp.rs:1111`), so write the butterfly with `fmaxf` (+112 SASS instructions and +1.5% in `flash_attn_rpb_d32` otherwise). `reduce_sum_f32` is fine.
- **No partial unrolling of a `blockDim.x`-step loop** (upstream #1691): nvcc unrolls it 4x, while cuda-oxide and clang leave it rolled. `#[unroll(N)]` on such an `i += step` loop is dropped with a warning and nothing reaches LLVM, and every call is exported `convergent`, which blocks LLVM's runtime unroller. Either write a counted loop (`for it in 0..n.div_ceil(threads)` with `#[unroll(4)]`), or loop to a fixed upper bound fully unrolled and skip the extra iterations with a test that folds after inlining. A full `#[unroll]` on a bound that is constant only after inlining warns, but LLVM may unroll it anyway. Cost 0.9% bandwidth-bound; flash tile staging was reported 27% slower at `2d47e43` (not re-measured).
- **Bounds-checked `slice[i]` in a loop can stop LLVM unrolling it** (14 loads issued together became 2; +2.9% in a bandwidth-bound warp-per-row dot product, more when latency is exposed): LLVM's multi-exit unroll policy. A view's `get(i)` checks against the loop bound once and unrolls. Read rows through `MatrixView32`/`RowView32`. Checks also cost registers (`roi_align` 40 to 45 for four checked loads), and the cuda-oxide book measures a naive GEMM 2.4x slower with checked indexing.
- **Block-uniform checks before the first load cost 4-7% in short block-per-row kernels** (sam3rs LayerNorm, 2-13 µs per launch, `88e52d117`). Each `MatrixView32::row` or length check is a constant-bank load, a 64-bit compare and an early `EXIT` in front of the first `LDG`. Fold all the checks into one non-short-circuit condition (`a & b & c`, one `return`), then read through a row pointer the check covers; that recovers about half the gap. `ld.global.nc` loads (rustc's `noalias` on `&[T]`, the same as nvcc's `const __restrict__`) and `get(c).unwrap_or(0.0)` (folded away) measured 0%.
- **Deriving a row length from a slice length in a block-per-row kernel** (`x.len() / gridDim.x`) puts an integer division before the first load of every block (72 against 48 instructions). Pass the row length as a param and let the view check it (layernorm_bf16 3% faster, `2d47e43`). One-thread-per-element kernels only compare against the length, so they are fine.
- **A gather that `DisjointSlice` forces can read strided:** sam3rs `transpose` of `[14400, 8]` took 1.58 against 1.11 µs as a scatter. It's the layout, not cuda-oxide. Keep the scatter, writing through `as_mut_ptr()` with a SAFETY comment, or use a shared-memory tiled transpose (1.10 µs there, and 5x faster than either at 5184 × 256).
- **A bounds check whose trap depends on the thread marks the warp divergent**: ptxas then wraps every later shuffle and `mma` in WARPSYNC/ENDCOLLECTIVE, the same as for nvcc's `__trap()`. On sm_80 it can show as SASS `CALL`s, ptxas's divergent-shuffle fallbacks. In warp-cooperative kernels, check once up front with a block-uniform condition and index unchecked after.
- **With llc-21 only** (none of these with the default LLVM 23):
  - Selecting between a real view and `RowView32::empty()`, or any pointer merged with null through `if`/`select`, turns the loads into generic `LD`. Keep an optional input as an empty slice and test `is_empty()`, or load inside the branch.
  - Iterating a local array by value (`for x in arr`) keeps it on the stack (32 bytes for 4 floats); `for x in &arr` or a counted loop doesn't.
- **Moving a kernel's code into shared helpers can change its SASS** with no stack or spills (`2d47e43`: +8 instructions in the BF16 flash kernels from a different block layout; related: upstream #1477, shared static names shift). When a kernel must stay unchanged, give the new kernel its own copies and diff the old kernel's PTX to byte-identical.
- **`cvt.rna.tf32.f32` costs 3 instructions per value on sm_120** (ptxas, as with nvcc's `__float_to_tf32`: an `FSETP` NaN/Inf guard, a predicated add of `0x1000`, a mask), which shows up as many `FSETP` in TF32 kernels. A bit-trick rounding saves only the guard and turns the canonical NaN `0x7fffffff` into -0.
- **Shared addresses for `ldmatrix`:** prefer `ldmatrix_*_shared_u32` with a per-lane u32 address computed once (upstream #1235). At `88e52d117` every constant-stride form compiles to the same SASS; a runtime-stride usize form costs about 16 setup instructions and 4 registers, with no measurable time. The "150 more instructions" seen in a flash kernel at `2d47e43` didn't reproduce in isolation.

## Open slowdowns

Measured, cause not confirmed. Test the suspects before trusting a fix.

- **`flash_attn_rpb_d32` +9% behind nvcc** (`88e52d117`, LLVM 23: 25.04 against 22.96 µs; +16% with llc-21, as sam3rs builds). The loads and results are the same, and the output is bit-identical. ptxas issues the 32 relative-position-bias loads in bursts of 1-3 (96 registers) where nvcc's PTX gets bursts of 9-12 (128 registers), so the bias adds stall on long scoreboard. Ruled out: layout flags, the `.nc` loads, the grid-wrap loop, FMA fusion. The PTX difference ptxas reacts to isn't found.

## Correctness traps

- `convert::f32_pair_to_packed_bf16` **truncates** (documented); `cvt_bf16x2_f32` rounds to nearest even.
- **A non-`move` closure that captures a shared-memory pointer and has a loop in its body fails MIR verification** (`88e52d117`, upstream #1689: "MirStoreOp value type must match pointer element type"). Write `move |..|`; no macro needed.
- **An unchecked read evaluated before the check that proves it.** `x.unwrap_or(unsafe { *w.get_unchecked(c) })`, or a `let` above an `if w.is_empty()`, reads eagerly: UB on an empty or short slice. Keep each unchecked read inside the branch that proves it in bounds.
- **The launch contract is only checked by cuda-oxide's own launcher.** Another host (cudarc, the driver API) must keep `grid x block <= 2^32` for 32-bit coordinates and push a length after every slice pointer itself.

## API gaps and limits

- `#[unroll]` is rewritten by the `#[kernel]`/`#[device]` macros, so inside a `macro_rules!` body or a plain helper fn it's a compile error ("cannot find attribute `unroll`"); use `__unroll_config::<N>()` there. On a loop with a non-constant step (`i += blockDim_x()`), `#[unroll(N)]` warns "no recognized induction variable" and the loop stays rolled.
- `#[unroll(N)]` on a loop that matches an `Option` (such as `view.get(i).unwrap_or(0.0)`) warns "early `break` or multiple exits" and is ignored: the match's `unreachable` arm counts as an exit (upstream #1690). LLVM usually unrolls such a view loop by itself. Bounds-checked `slice[i]` loops are not affected.
- `ThreadIndex32` is not `Copy` (by design), so each output `DisjointSlice` needs its own witness: call `thread::index_1d_u32(lc)` once per slice.
- No block-indexed output space (upstream #1692; PR #1585 adds one scalar per block): a block that owns a row writes through `DisjointSlice::get_unchecked_mut` with a SAFETY comment. A kernel that reads and writes one buffer can't take it as both `&[T]` and `DisjointSlice<T>` (that aliasing is UB): split an in-place kernel that takes only the `DisjointSlice` (it reads through the slice's raw pointer, since two closures can't share `get_unchecked_mut`).
- A `DisjointSlice` is written only at the thread's own index: a scatter kernel becomes a gather over the output (so its reads may stride, see the transpose entry), and a thread with two outputs either takes a second witness or writes one combined buffer.
- Wide loads and stores need no asm: the element type's alignment decides. Use `cuda_device::vector::F32x4` (or a `repr(C, align(8|16))` type) in a `&[T]`, `DisjointSlice<T>` or `SharedArray<T, N>`, or `vector::as_vectors` on a flat slice, for `LDG.E.128`, `st.global.v4`, `STS.128` and `LDS.128`, even when the lanes are read after. `DisjointSlice` params print `.ptr .align 1`, as nvcc's `float*` params do, and that doesn't matter. The `vector` module's doc table saying lane reads split into scalar loads is stale (upstream #1694).
- No bf16 value type in cuda-device (upstream #1695): the `bf16`/`bf16x2` intrinsics take `u16`/`u32` bits, so wrap them in a newtype with the `convert` functions.
- No `static mut SharedArray` in generic fns (Rust E0401): declare tiles per kernel and pass pointers in, or use `DynamicSharedArray`.
- No `[T; D / 16]` in generics without `generic_const_exprs`: pass the derived length as another const param.
- `f32::mul_add` isn't in stable `core` (only the unstable `core::f32::math::mul_add`): use `float::fma_rn_f32`, or `a * b + c`, which contracts to `fma.rn`. For libdevice math call `libm::erff` and friends (dependency `libm`): since #1660 (in `2d47e43`) cuda-oxide lowers 120 libm exports to libdevice, so hand-written `extern "C" __nv_*` declarations are unnecessary. `__nvvm_reflect("__CUDA_FTZ")` resolves to the non-FTZ branch, nvcc's default.
- No safe empty `DisjointSlice` (upstream #1693): `unsafe { DisjointSlice::from_mut_slice(&mut []) }` with a SAFETY note is sound. `launch_contract(block = ...)` emits `.reqntid` and no `.maxntid`, by design: ptxas forbids both on one entry.
- Tensor-core wrappers are split across files: `cuda_device::wmma` has `mma_m16n8k16_f32_bf16`, `_f32_f16`, `_f16_f16` (FP16 accumulate, from `generated/register_mma.rs`), `mma_m16n8k8_f32_tf32` and `mma_m16n8k4_f32_tf32` (PTX has no dense k16 TF32 shape; `convert::cvt_rna_tf32_f32` rounds), `ldmatrix_*` and the `mma_frag` accumulator layout helpers (`2d47e43`). Search the crate source, including `generated/`, before writing `ptx_asm!`.
- `ldmatrix_x4_shared_u32` over FP32/TF32 rows (row stride D + 4 words keeps it conflict free) gives lane (g, t) word t of row g, which is exactly the m16n8k8 TF32 A and B fragment layout; the S accumulator then serves as the P @ V A fragment as `{s0, s2, s1, s3}` with V read at rows 2t and 2t + 1.
- A host that launches slice-ABI kernels should check its arguments against each `.entry` param list read from the PTX text it loaded (`.u64 .ptr` address, `.u64` length, `.u32`, `.f32`; `i32` params are declared `.u32` too), once per kernel. Probing `cuFuncGetParamInfo` past the last param returns `CUDA_ERROR_INVALID_VALUE`, which compute-sanitizer reports as an API error for every kernel, and `cuFuncGetParamCount` needs CUDA 13.2.
- `#[kernel] pub unsafe fn` with raw pointers and plain scalars exports a C-like entry, so hosts written for CUDA C++ kernels need no launch changes.

## Checks on every build

Scripts in this skill's `scripts/` folder:

- `sass_mix.sh REF.ptx NEW.ptx [ARCH] [KERNEL...]`: calls left in each PTX, then per kernel the registers, stack, spills, SASS instruction count and trap opcodes (generic `LD`, `FSETP`+`FSEL`, `LDL`/`STL`). With no kernels, every kernel whose registers or spills changed. CPU only.
- `nsys_kernel_diff.py CTL.sqlite[,...] EXP.sqlite[,...] [N]`: per-kernel GPU time of two builds from nsys SQLite exports (`--export=sqlite`, both builds profiled through the GPU queue with the same command, interleaved), the N biggest wins and losses.

- No `call` in the PTX (libdevice is inlined, so any call is a body that wasn't); fail the build on it.
- ptxas `-v`: no unexpected spills or stack frames. A 32-byte stack in a kernel calling `sinf`/`cosf` is libdevice's slow path, the same as nvcc's.
- A refactor with byte-identical PTX is safe; diff it.
- When porting or changing codegen, compare `cuobjdump -sass` opcode counts per kernel with the reference build, and run an nsys per-kernel diff plus an A/B in every precision mode: parity and sanitizers miss speed regressions.
