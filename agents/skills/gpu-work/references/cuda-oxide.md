# cuda-oxide watch-outs

Traps that cost correctness or speed in cuda-oxide kernels, and the checks that catch them. The user maintains it: don't edit it during a task; log new traps in the decision log instead. Each entry is one line per trap with the fix, plus the commit it was seen at, since some are bugs that later commits may fix. Recheck old entries when you move to a newer cuda-oxide. A slowdown you measured but couldn't explain goes under "Open slowdowns" with its suspects, until a test confirms a trap or clears it.

## Coverage

The entries come from one codebase (sam3rs, about 50 kernels: elementwise, norms, convs, flash attention on BF16 and TF32 tensor cores) on one GPU (RTX 5090, sm_120); the sm_80 tier was checked in SASS only, never run on Ampere. Not yet exercised, so expect unlisted traps there: atomics, grid-wide reductions and cooperative launches, TMA and `wgmma` (sm_90+), FP8, thread-block clusters.

## Version

Use `praveenperera/cuda-rust` `master` at `a5c86a293`.

When moving the pin, rebuild the old and new pins and run `sass_mix.sh` over every kernel; time any kernel whose registers moved. The move to `4c0182cd5` raised every flash kernel's registers unnoticed (Open slowdowns).

## Setup

- Use a project-owned `CARGO_HOME` for cargo-oxide: the backend cache in `$CARGO_HOME/cuda-oxide/` has one slot, rebuilt whenever a project's `cuda-device` dependency resolves to another commit (`source-rev.txt`).
- Pin the commit in the kernel crate's `Cargo.lock`; the backend is built from that dependency checkout. Install cargo-oxide at the same commit so the CLI matches too. The toolchain is whatever that commit's `rust-toolchain.toml` pins.
- `cargo oxide build` builds the backend when its cache is missing or stale, so a build script needn't call `cargo oxide setup`. In a standalone crate, `setup` rebuilds the backend from the commit your `cuda-device` dependency resolves to even when the cache is fresh (a path dependency builds in place), and it refuses when `CUDA_OXIDE_BACKEND` or `.cargo/cuda-oxide.toml` pins the backend. `build` recompiles the crate and rewrites the PTX every run when its root is `src/lib.rs` or `src/main.rs`; with another root, check the PTX timestamp.
- Use the toolchain's own llc (LLVM 23.1.1 at `88e52d117`), the default. With `CUDA_OXIDE_LLC=llc-21`, several traps below appear that LLVM 23 doesn't have, and `flash_attn_rpb_d32` is 6% slower.
- **A missing toolchain llc falls back silently.** cuda-oxide probes `CUDA_OXIDE_LLC`, then the sysroot's llvm-tools llc, then `llc-23`/`llc-22`/`llc-21`/`llc` on PATH, with no warning. A toolchain reinstall that dropped the `llvm-tools` component moved the codegen of 31 of 66 sam3rs kernels with no source change, and read as a perturbation from the edit under test. `cargo +<toolchain>` and `rustup run` ignore the components list in `rust-toolchain.toml`, so nothing reinstalls it. The build script should set `CUDA_OXIDE_LLC` to `$(rustc +T --print sysroot)/lib/rustlib/<host>/bin/llc` and fail when that file is missing (sam3rs `scripts/build-ptx.sh`). A toolchain cleanup job that prunes "old" rustup toolchains removes the pinned one outright (twice on 2026-11-01, from a weekly and a monthly cron), and rustup's auto-install brings it back without llvm-tools; re-add the components (`rustup component add rust-src rustc-dev llvm-tools --toolchain T`) and keep the pin out of such jobs.
- The PTX ISA `.version` sets the minimum driver; check it in the build script (7.0 for sm_80, 8.7 for sm_120, with LLVM 21 and 23).

## Speed traps

- **A generic `#[device]` fn without an inline attribute is inlined only if LLVM finds it small**: a large body stays a `.func` and its pointers arrive generic (generic `LD` instead of `LDS`/`LDG`: +26% in a repro; `flash_combine_d32` +72% in sam3rs until inlined). Mark hot generic `#[device]` helpers `#[inline(always)]`, which they obey (`#[inline(never)]` keeps a `CALL`). A generic `#[device] #[inline(always)]` in a crate with no kernels, instantiated only from host code, is dropped at release opt.
- **A borrow (`mir.ref`) of a local inside a loop gets its stack slot at the use site**, not in the entry block, and LLVM treats an alloca outside `entry:` as dynamic: it won't inline the function and SROA leaves the slot on the stack. If a `.func` or a frame appears with no obvious reason, check the IR for an `alloca` outside `entry:`.
- **`core::iter::Zip` over a slice iterator and a view iterator is 2.15x slower than a counted loop**: its loop has two exits, so LLVM leaves it rolled with one load in flight per thread. Use a counted loop over views. `zip_exact` is fine on LLVM 23 but stays rolled with llc-21.
- **An inline helper returning `Option<(struct, views...)>` put the payload on the stack** (a 304-byte frame with `LDL`/`STL` in every sam3rs flash kernel that called it; not rechecked on the pinned commit). Return a plain tuple and `unreachable_unchecked()` past the one up-front check, or check `ptxas -v` for a frame.
- **A loop LLVM leaves rolled puts every register array it indexes on the stack**: a `[F32x4; N]` row cache, or a vector's `.0[e]`, indexed by the loop counter needs constant indices, so a loop that isn't fully unrolled sends the whole array to `.local`. Short libdevice loops unroll on their own (a 4-step fill calling `libm::erff` stays in registers), but an 8-step pass over a row cache calling `expf` stays rolled, and so can any loop with a large body. When the loop's bound is a literal, an optimized build warns: "local `v` ... could not be promoted to registers ... indexed by the counter of a loop LLVM did not unroll". With a runtime bound or in a debug build there is no warning, so check `ptxas -v`. Put `#[unroll]` on every loop that indexes a register array, or build the vector with an array constructor (`F32x4([f(a.0[0]), f(a.0[1]), ..])`). A conditional load into a mutable zero (`let mut b = zero; if c { b = load }`) didn't frame.
- **64-bit index math** (`i64` indices, as ported from `long long`) compiles `/` and `%` to ptxas's 64-bit divide sequence (nvcc's is no better). 32-bit coordinates (`thread::index_1d_u32`, `element_thread32`, `#[launch_contract(coordinates = u32)]`) divide inline: 20-70% fewer instructions in elementwise and conv kernels, though memory-bound kernels time the same.
- **`f64::max`/`min` compile to compare + select**, not one `max.f64` (`libm::fmax`/`fmin` too), and so does `f32` on the libNVVM route. On the default route `f32::max`/`min` and `warp::reduce_max_f32`/`reduce_min_f32` are one `max.f32`/`min.f32`.
- **`#[unroll(N)]` partially unrolls block-stride loops.** It takes a counted-up `<`/`<=` loop with a runtime start and a positive constant or loop-invariant runtime step (`i += blockDim_x()`), and a bound the loop recomputes from fixed values (`while i < n as usize`). A group of N copies runs only when the loop's test passes for every counter in it, and the original loop runs the rest. A `match` in the body, such as `row.get(i).unwrap_or(0.0)`, is not an extra exit, but a `break` is. Full `#[unroll]` still needs a constant start and step. Per-thread intrinsics such as `threadIdx_x()` are no longer exported `convergent`, so LLVM may runtime-unroll an unannotated block-stride loop itself (not measured); annotate the loop when the unroll matters.
- **Bounds-checked `slice[i]` in a loop can stop LLVM unrolling it** (14 loads issued together became 2; +2.9% in a bandwidth-bound warp-per-row dot product, more when latency is exposed): LLVM's multi-exit unroll policy. A view's `get(i)` checks against the loop bound once and unrolls. Read rows through `MatrixView32`/`RowView32`. Checks also cost registers (`roi_align` 40 to 45 for four checked loads), and the cuda-oxide book measures a naive GEMM 2.4x slower with checked indexing.
- **Block-uniform checks before the first load cost 4-7% in short block-per-row kernels** (sam3rs LayerNorm, 2-13 µs per launch, `88e52d117`). Each `MatrixView32::row` or length check is a constant-bank load, a 64-bit compare and an early `EXIT` in front of the first `LDG`. Fold all the checks into one non-short-circuit condition (`a & b & c`, one `return`), then read through a row pointer the check covers; that recovers about half the gap. `ld.global.nc` loads (rustc's `noalias` on `&[T]`, the same as nvcc's `const __restrict__`) and `get(c).unwrap_or(0.0)` (folded away) measured 0%.
- **Deriving a row length from a slice length in a block-per-row kernel** (`x.len() / gridDim.x`) puts an integer division before the first load of every block (72 against 48 instructions). Pass the row length as a param and let the view check it (layernorm_bf16 3% faster, `2d47e43`). One-thread-per-element kernels only compare against the length, so they are fine.
- **A gather that `DisjointSlice` forces can read strided:** sam3rs `transpose` of `[14400, 8]` took 1.58 against 1.11 µs as a scatter. It's the layout, not cuda-oxide. Keep the scatter, writing through `as_mut_ptr()` with a SAFETY comment, or use a shared-memory tiled transpose (1.10 µs there, and 5x faster than either at 5184 × 256).
- **A bounds check whose trap depends on the thread marks the warp divergent**: ptxas then wraps every later shuffle and `mma` in WARPSYNC/ENDCOLLECTIVE, the same as for nvcc's `__trap()`. On sm_80 it can show as SASS `CALL`s, ptxas's divergent-shuffle fallbacks. In warp-cooperative kernels, check once up front with a block-uniform condition and index unchecked after.
- **With llc-21 only** (none of these with the default LLVM 23):
  - Selecting between a real view and `RowView32::empty()`, or any pointer merged with null through `if`/`select`, turns the loads into generic `LD`. Keep an optional input as an empty slice and test `is_empty()`, or load inside the branch.
  - Iterating a local array by value (`for x in arr`) keeps it on the stack (32 bytes for 4 floats); `for x in &arr` or a counted loop doesn't.
- **Moving a kernel's code into shared helpers can change its SASS** with no stack or spills (+8 instructions in the BF16 flash kernels from a different block layout). Shared statics and device globals are named from a hash of the static's symbol in every build (`__shared_mem_<crate>_<hash>`, `__device_global_<crate>_<hash>`), so adding, removing or reordering kernels doesn't rename them. Each `SharedArray` field of a struct, tuple, union, enum or array static gets its own storage, and a static with two same-type `SharedArray` or `Barrier` fields at one offset is refused at compile time: give each its own static. Names that can still move: `$L__BB<n>_` labels, `// @<name>` comments, the numbered `__shared_mem_<n>` of keyless shared allocations, and for now the globals behind a `const` reference to a non-array value (`const P: &(u32, u32) = &(3, 4)`), which follow rustc's allocation numbering. Diff per entry after normalizing them (`PW/ops/sam3rs/hill-climb/ptx_same.py`) before calling a kernel changed. When a kernel must stay unchanged, give the new kernel its own copies and diff the old kernel's PTX to byte-identical.
- **`cvt.rna.tf32.f32` costs 3 instructions per value on sm_120** (ptxas, as with nvcc's `__float_to_tf32`: an `FSETP` NaN/Inf guard, a predicated add of `0x1000`, a mask), which shows up as many `FSETP` in TF32 kernels. A bit-trick rounding saves only the guard and turns the canonical NaN `0x7fffffff` into -0.
- **Shared addresses for `ldmatrix`:** prefer `ldmatrix_*_shared_u32` with a per-lane u32 address computed once. At `88e52d117` every constant-stride form compiles to the same SASS; a runtime-stride usize form costs about 16 setup instructions and 4 registers, with no measurable time. The "150 more instructions" seen in a flash kernel at `2d47e43` didn't reproduce in isolation.

- **Under one wave, ptxas can save registers for occupancy the grid never uses, and serialize loads to fit.** `flash_attn_rpb_d32` at the sam3rs decoder shape (448 blocks, 0.53-0.66 waves on a 5090) got 96 registers and issued the last 16 of its 32 bias loads two at a time, each pair waited on before the next: 25.10 µs against nvcc's 23.01, where nvcc's PTX got 128. nvcc's PTX capped at 96 registers ran 26.57 µs. `.minnctapersm 1` (which `#[launch_bounds(128, 1)]` emits; tested by editing the PTX) or `.maxnreg 128` gave 115 registers and 22.38 µs, 2.7% ahead of nvcc, with bit-identical output (`88e52d117`). It didn't help at `4c0182cd5` (see Open slowdowns). When a latency-bound kernel's grid is under a wave at every deployed shape, try the min-blocks bound; above a wave it trades occupancy, so time it. Diagnose from the SASS scoreboard bits rather than load counts: how many loads are in flight at each wait.

## Open slowdowns

Measured, cause not confirmed. Test the suspects before trusting a fix.

- **`4c0182cd5` regressed the flash-attention kernels against `88e52d117`.** `flash_attn_rpb_d32` went from 25.10 to 26.04 µs (13.1% behind nvcc), with output unchanged. Registers rose in every flash kernel, with no spills: `flash_attn_d32` 80 to 128, `kv16_d32` 80 to 98, `bf16_d64` 137 to 162, `d64` 152 to 176. In rpb every bias load now issues in a pair, and no register directive restores the overlap. Bisected to `acd66a84f` (upstream PR #1721, open): special-register reads (`tid`, `ctaid`) are no longer exported `convergent`, so LLVM hoists the thread-derived `ldmatrix` addresses out of the key loop and keeps each one live. Restoring `convergent` on those reads alone gives back every old register count; on the 786 `llvm.trap` calls it changes nothing. Only rpb was timed. Until it's resolved, time each flash kernel against a `cb3df85aa` build before trusting a number from this pin.

## Correctness traps

- `convert::f32_pair_to_packed_bf16` **truncates** (documented); `cvt_bf16x2_f32` rounds to nearest even.
- **An unchecked read evaluated before the check that proves it.** `x.unwrap_or(unsafe { *w.get_unchecked(c) })`, or a `let` above an `if w.is_empty()`, reads eagerly: UB on an empty or short slice. Keep each unchecked read inside the branch that proves it in bounds.
- **The output witness consumes `ThreadIndex32`, which invites reading the input first.** `let v = x[t.get()]` above `element_thread32(t)` runs on the tail threads the witness would reject and traps (sam3rs `mask_for_mem`, latent while every length was a multiple of 256). Take `let i = t.get() as usize` first, then the witness, then the read
- **The launch contract is only checked by cuda-oxide's own launcher.** Another host (cudarc, the driver API) must keep `grid x block <= 2^32` for 32-bit coordinates and push a length after every slice pointer itself.
- A `const` reference (`const C: &T = &...`) or a promoted borrow (`&42`) is a read-only global, so a device fn, even `#[inline(never)]`, can return it. A `*mut` cast from one points at read-only storage: only read through it.
- A const, constant table or static whose type holds a pointer to shared memory (`SharedArray`, `Barrier`) is refused ("stores a pointer to shared memory") whenever the value stores any pointer. Pass shared pointers as arguments, or build the value at run time.
- A shared-memory pointer stored through a generic pointer place (a deref, field, array element, call destination or `write_volatile`) is widened to a generic address. A store that would narrow a generic pointer into a shared-typed place still fails MIR verification.

## API gaps and limits

- `#[unroll]` is rewritten by the `#[kernel]`/`#[device]` macros, so inside a `macro_rules!` body or a plain helper fn it's a compile error ("cannot find attribute `unroll`"); use `__unroll_config::<N>()` (0 = fully, N = by N) as the loop body's first statement there, and recheck it after every cuda-oxide upgrade, since it's the undocumented call `#[unroll]` expands to. `__unroll_config::<0>()` in an inner loop that starts at an outer loop's variable (`kk` from `c0` to `c0 + N`) warns and stays rolled even when the outer loop unrolls, which spilled 84 B in a d256 flash kernel: loop `i` over `0..N` and use `kk = c0 + i`.
- An unroll clones at most 65,536 operations, counted after inner annotated loops expand; an outer loop around a few fully unrolled inner loops goes over, stays rolled with a warning, and moves any local array it indexes to `.local`. `#[unroll(max_ops = M)]` or `#[unroll(N, max_ops = M)]` sets that loop's operation cap, and the warning names the `max_ops` the loop needs; the 1,024-copy and 8,192-block caps stay. A big unroll still costs: one such kernel used 255 registers, spilled 1288 B and took 258 s to lower, so check `ptxas -v`, or split the loop.
- `ThreadIndex32` is not `Copy` (by design), so each output `DisjointSlice` needs its own witness: call `thread::index_1d_u32(lc)` once per slice.
- For a block-per-row kernel (LayerNorm, softmax), take the output as `DisjointSlice<T, BlockRows>` and bind the row width on the host with `cuda_host::RowWidth::new(&mut buf, width)`. In a kernel with `#[kernel(launch_context = lc)]` and `#[launch_contract(domain = 1, coordinates = u32, ..)]`, `out.block_row32(lc)` gives block b row b, and `row.thread_columns()` yields the thread's columns t, t + blockDim.x, ... as witnesses with `read()`, `write()` and `column()`. An in-place kernel takes only that slice and reads through the witnesses; don't also take the buffer as `&[T]` (that aliasing is UB). `block_row32` returns `None` for the whole block on a partial last row or width 0, so the early return can't strand part of a block at a barrier.
- A `DisjointSlice` is written only at the thread's own index: a scatter kernel becomes a gather over the output (so its reads may stride, see the transpose entry), and a thread with two outputs either takes a second witness or writes one combined buffer.
- Wide loads and stores need no asm: the element type's alignment decides. Use `cuda_device::vector::F32x4` (or a `repr(C, align(8|16))` type) in a `&[T]`, `DisjointSlice<T>` or `SharedArray<T, N>`, or `vector::as_vectors` on a flat slice, for `LDG.E.128`, `st.global.v4`, `STS.128` and `LDS.128`, even when the lanes are read after. `DisjointSlice` params print `.ptr .align 1`, as nvcc's `float*` params do, and that doesn't matter. Reading only some lanes lets LLVM narrow the load to those lanes.
- No bf16 value type in cuda-device: the `bf16`/`bf16x2` intrinsics take `u16`/`u32` bits, so wrap them in a newtype with the `convert` functions.
- No `static mut SharedArray` in generic fns (Rust E0401): declare tiles per kernel and pass pointers in, or use `DynamicSharedArray`.
- No `[T; D / 16]` in generics without `generic_const_exprs`: pass the derived length as another const param.
- `f32::mul_add` isn't in stable `core` (only the unstable `core::f32::math::mul_add`): use `float::fma_rn_f32`, or `a * b + c`, which contracts to `fma.rn`. For libdevice math call `libm::erff`, `libm::sqrtf` and friends (dependency `libm`): cuda-oxide lowers 120 libm exports to libdevice, so hand-written `extern "C" __nv_*` declarations are unnecessary. `__nvvm_reflect("__CUDA_FTZ")` resolves to the non-FTZ branch, nvcc's default.
- For an optional output, pass `DisjointSlice::empty()` (const) or `Default::default()`: every accessor returns `None`. Pass it by value or as `&mut DisjointSlice::empty()`; a reference to a `const` holding a `DisjointSlice` is a compile error. `launch_contract(block = ...)` emits `.reqntid` and no `.maxntid`, by design: ptxas forbids both on one entry.
- Tensor-core wrappers are split across files: `cuda_device::wmma` has `mma_m16n8k16_f32_bf16`, `_f32_f16`, `_f16_f16` (FP16 accumulate, from `generated/register_mma.rs`), `mma_m16n8k8_f32_tf32` and `mma_m16n8k4_f32_tf32` (PTX has no dense k16 TF32 shape; `convert::cvt_rna_tf32_f32` rounds), `ldmatrix_*` and the `mma_frag` accumulator layout helpers (`2d47e43`). Search the crate source, including `generated/`, before writing `ptx_asm!`.
- `ldmatrix_x4_shared_u32` over FP32/TF32 rows (row stride D + 4 words keeps it conflict free) gives lane (g, t) word t of row g, which is exactly the m16n8k8 TF32 A and B fragment layout; the S accumulator then serves as the P @ V A fragment as `{s0, s2, s1, s3}` with V read at rows 2t and 2t + 1.
- A host that launches slice-ABI kernels should check its arguments against each `.entry` param list read from the PTX text it loaded (`.u64 .ptr` address, `.u64` length, `.u32`, `.f32`; `i32` params are declared `.u32` too), once per kernel. Probing `cuFuncGetParamInfo` past the last param returns `CUDA_ERROR_INVALID_VALUE`, which compute-sanitizer reports as an API error for every kernel, and `cuFuncGetParamCount` needs CUDA 13.2.
- An associated `const` of a struct that holds `&[T]` slices (`const NONE: Rope = Rope { cos: &[], .. }`) fails device codegen: "Aggregate slice constant ... slice provenance currently requires a Rust device static". Build the value in an `#[inline(always)] fn none() -> Self` with inline `&[]` literals instead.
- `#[kernel] pub unsafe fn` with raw pointers and plain scalars exports a C-like entry, so hosts written for CUDA C++ kernels need no launch changes.

## Checks on every build

Scripts in this skill's `scripts/` folder:

- `sass_mix.sh REF.ptx NEW.ptx [ARCH] [KERNEL...]`: calls left in each PTX, then per kernel the registers, stack, spills, SASS instruction count and trap opcodes (generic `LD`, `FSETP`+`FSEL`, `LDL`/`STL`). With no kernels, every kernel whose registers or spills changed. CPU only.
- `nsys_kernel_diff.py CTL.sqlite[,...] EXP.sqlite[,...] [N]`: per-kernel GPU time of two builds from nsys SQLite exports (`--export=sqlite`, both builds profiled through the GPU queue with the same command, interleaved), the N biggest wins and losses.

- No `call` in the PTX (libdevice is inlined, so any call is a body that wasn't); fail the build on it.
- ptxas `-v`: no unexpected spills or stack frames. A 32-byte stack in a kernel calling `sinf`/`cosf` is libdevice's slow path, the same as nvcc's.
- A refactor with byte-identical PTX is safe; diff it.
- When porting or changing codegen, compare `cuobjdump -sass` opcode counts per kernel with the reference build, and run an nsys per-kernel diff plus an A/B in every precision mode: parity and sanitizers miss speed regressions.
