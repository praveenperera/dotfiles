# Track F: agent-run kernel work

Running workers, advisors or reviewers on kernel tasks. Shorthands as in SKILL.md.

- The root copies the rules that apply into `PW/playbooks/kernel-worker-brief-template.md`, so workers get a bounded brief with stop rules, attempt caps, known risks, and the ambitious design to build first. Word briefs precisely, because workers read them literally: "don't publish during verification" was read as "rewrite the publish recipe".
- The root owns the decision log. Workers report decisions and rule candidates; the root logs them, and the user decides what goes into the skill.
- **Use two model families for different jobs.** Sol forecasts best (6 confirmed against 4 for Opus); Opus diagnoses best from raw nsys SQLite and takes bolder numerical routes that need audits. Run both on different routes for hard problems, Opus behind a wall-time limit (one run took 1.5 h plus a 3 h hang). Use xhigh for Sol; ask the user before running Opus at xhigh.
- **Give every advisor the same files, card, build and an idle-GPU trace**, and score them against measurements. Partial results, mixed baselines (A100 PCIe against SXM4) or contended traces make calls unscoreable. More project context didn't help: the advisor with the most ranked last.
- **Reject any end-to-end forecast that is a peak ratio times a kernel share.** Every advisor got two such forecasts wrong; those who computed unions and spans from the trace did better. Ask for a measure-first list ranked by cost, and run its cheap probes: a skipped 30-minute MMA microbenchmark left a later FP16 loss unattributable.
- **Build what the advisor specified, or record the deviation.** A v1 used m16n8k8 where both advisors named m16n8k16, and the shortfall can no longer be pinned on the hardware or the kernel.
- **Review correctness with another model family between phases.** Sol found 14 issues in one runtime, including a reproduced panic, where 17 automated security passes found nothing that held up, and 3 P1 safety issues in a crate whose tests and CI passed. Give the reviewer the upstream repo and ask about math, odd shapes and API misuse.
- Workers fix their own scratch bugs and rerun without asking. Diff every worker change against its brief, and integrate with every dependency on day one, against the real gate. Codex workers can't receive mid-run messages: write briefs that need no answers, or cancel and relaunch with a resumed brief.
- **Give shared infrastructure one owner.** When two runs touch the same harness, one holds it and the other sends requirements; split kernel ownership by area so branches don't collide.
- A T3 subagent never queues long GPU work. A child thread or a homebased worker owns each GPU job: it submits the job and waits the way "Long work" in the use-agents skill says for its runner. A child thread sleeps with `homebased wait --long`, and a homebased worker reports `waiting --on <job-id>` and exits. The job's events resume its owner, even after it reported done. Don't edit its files meanwhile; route follow-ups through it.
- Give each session that builds and times GPU binaries its own worktree. Before freezing binaries, check that every file changed since the last freeze is yours, or snapshot the source you built. When workers each regenerate shared PTX, merge their kernel sources and rebuild once, then diff that only their kernels changed.
- Keep raw profiler output (`.nsys-rep`, `.sqlite`) out of git; files over 100 MB forced a history rewrite.
