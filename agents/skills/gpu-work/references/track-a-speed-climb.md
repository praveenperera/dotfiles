# Track A: speed climb

Making kernels or a pipeline faster: a contest (OKC) or a hill climb on our runtimes. `R` = `~/code/research/gpu-kernels/`, `PW` = `~/code/private-workbench/`.

- The ambition rule in SKILL.md "Be ambitious" applies in full: about 70% of the budget on one or two rewrites aimed at the floor, 30% on tuning and integration, rewrites judged by their ablation ceiling within an hour (no compute, no reduce, no secondary loads).
- Skip experiments whose expected gain is below the noise. Rewrite the largest share first.
- Measure real hardware floors before trusting specs: H200 cold-L2 reads reached 3.6 of 4.8 TB/s.
- Measure the instruction issue rate before trusting "pipe saturated". m16n8k16 FP16 issues at the same rate as k8, which doubled throughput.
- Sample power and clock-event reasons during the timed run (`nvidia-smi --query-gpu=power.draw,clocks.sm,clocks_event_reasons.active -lms 20`) before counting idle issue slots as headroom. sam3rs's FP32 encode ran at the RTX 5090's 575 W cap at 2.6 of 2.9 GHz with the FMA pipe 55-61% busy; there, only fewer joules per FLOP buys speed. ncu locks base clocks and hides this.
- When kernels overlap on the GPU, end-to-end wins need less total SM occupancy, not a faster kernel in isolation.
- Size a SIMT (FP32 FMA) tile by shared-memory wavefronts, not occupancy: a 16-byte warp load costs 4 or more wavefronts even when lanes broadcast, so an R x C register piece caps at RC / 4(R + C) of the FMA rate (50% for 4x4, 67% for 8x4). In sam3rs's FP32 flash attention, a second block per SM changed nothing and 8x4 pieces took 18.0 to 16.5 ms (`~/code/research/inference/specialized-model-runtimes/sam3rs-decisions.md`).
- Run an A/A hash check before a bit-identity guard on any mode with timing-based autotune: sam3rs TF32's near-tie cuBLASLt choices gave one binary two output hashes across processes. Guard such modes with a parity-limit gate.
- A faster MMA doesn't help a kernel whose schedulers lack warps. sam3rs's head-dim-256 attention runs one 4-warp block per SM (255 registers, 101 KB shared), so one warp per scheduler; ncu read 64% tensor-pipe active with math-throttle and wait stalls on top, and its 20 B spill hit L1. FP16-accumulated QK^T, picked without that reading, bought 10% of the kernel (0.45 of 4.22 ms an object) instead of the 1.5x the rate promised, and failed the f64 gate. Check warps per scheduler and the top stalls in ncu before raising a pipe's rate. Where ncu does read the tensor pipe as the limit (the tracker's 64-wide-V cross-attention: 83% rate-weighted, math throttle the top stall, two warps a scheduler), FP16-accumulate steps of one m16n8k16 (16 terms) added into FP32 took the kernel from 592 to 447 µs at 7.6e-4 f64 error; 32-term steps crossed the 1e-3 bound. Price the step width on the f64 kernel test before timing (`~/code/research/inference/specialized-model-runtimes/sam3rs-decisions.md`, 2026-11-01)
- Count the format round trips around a GEMM before expecting its precision's rate. sam3rs's tracker linears moved from TF32 to BF16 and gained 0.2 of their 1.2 ms an object, since each GEMM still converted FP32 inputs and wrote FP32 outputs that the next kernel re-read
- When a climb lands several steps at once, build one control per step from a source copy with the later steps switched off (`if false`, a threshold set to its maximum), so each step gets its own ABBA verdict and A/B fingerprint
- Profile a `torch.compile(dynamic=True)` baseline at batch 1 before calling compile a win or a loss. On Kokoro, Inductor ran the AdaIN instance-norm reductions as 256 blocks of 64 threads (1% SM throughput, 368 µs a call), which doubled batch-1 latency while the same code gave 2.4x at batch 8 (`~/code/research/inference/specialized-model-runtimes/kokoro-baselines-2026-11-01.md`)
- Pass `--kernel-name-base demangled` when filtering ncu with `--kernel-name regex:`. By default it matches the bare function name, which for cuBLAS gemv and CUTLASS kernels is `kernel` or `Kernel2`, so those kernels silently never get profiled (`~/code/research/inference/specialized-model-runtimes/kokoro-baselines-2026-11-01.md`)
