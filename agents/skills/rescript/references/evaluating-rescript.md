# Evaluating whether ReScript paid off

Use this reference when assessing a migration, case study, or claim that ReScript reduced defects,
tokens, or delivery time. Preserve evidence about what existed before the migration and what was
introduced during it.

## Establish a baseline

Before changing languages:

1. record the revision and working behavior
2. run relevant compiler, unit, browser, and integration checks
3. preserve a minimal reproduction for every suspected existing defect
4. record source size, build time, agent tokens, repair iterations, and wall time only when those
   measures matter to the evaluation
5. list the intended language boundary and expected interop cost

Count authored ReScript implementations, interfaces, retained JavaScript/TypeScript adapters,
framework templates, tests, generated TypeScript, and generated JavaScript separately. Record
added dependencies and raw generated bytes when artifact cost matters. Do not describe deleted
TypeScript as a reduction without reporting the ReScript, interfaces, and adapters that replaced
it.

Do not use authored line count as a proxy for agent tokens. Generated code, bindings, comments,
tests, and a more explicit model can increase source size while reducing later repair work.

## Keep an evidence ledger

Classify each finding before claiming that the compiler caught it:

| Classification | Required evidence |
| --- | --- |
| pre-existing defect | reproduce it on the original implementation or revision |
| existing validation weakness | show an input the old boundary accepted and the new boundary rejects |
| migration mistake prevented | compiler error occurred only while translating or propagating a change |
| migration trap introduced | new risk came from ReScript, its numeric model, bindings, or build lifecycle |
| test or browser finding | a test, hydration check, or runtime inspection found it rather than the compiler |
| stronger model without observed defect | the new type excludes a plausible state, but no old failure was reproduced |
| tooling or interop cost | record bindings, adapters, generated files, watcher work, or build changes |

Do not collapse migration friction into “bugs ReScript caught.” Compiler errors can still be
valuable because they prevent new defects, but that is a different claim from finding an existing
bug.

## Measure the intended saving

If the claim is that ReScript saves agent tokens, measure or compare:

- total agent tokens across implementation, compiler repair, tests, and review
- number and size of compiler-guided repair loops
- runtime-debugging and browser-debugging loops avoided
- defects remaining after equivalent verification
- future change effort when a domain state or protocol evolves
- setup, binding, and adapter work added by the language boundary

Treat lower token use as a hypothesis, not a property of the language. The strongest evidence is
fewer LLM-led repair iterations because the compiler localized mismatches early.

After moving a boundary, re-audit its callers. A TypeScript renderer or orchestrator may have been
justified only because one of its dependencies was still external. Conversely, stop when moving
the remaining effect sequence would require more callback bindings than reusable policy.

## Review semantic and runtime gaps

Ask separately:

- did the new domain model preserve origin, authority, lifecycle, and legal transitions?
- were numeric ranges and JavaScript representations modeled correctly?
- were externals checked against runtime exports and nullability?
- did browser tests cover hydration timing, initial URLs, persistence, and external events?
- did a real source edit prove that the development watcher regenerates output?
- did string-backed variants receive behavior tests for their literal values?
- did route and method classifiers receive contract tests for their exact path and method strings?
- did binary output receive parity, signature, size, and metadata checks?
- did Worker or persisted-state tests use isolated state when old local schemas were irrelevant?
- when migrations were in scope, did tests cover both representative legacy state and fresh state
  while checking actual columns and constraints rather than trusting a version number?
- do static fallback and hydrated renderers use unique IDs while retaining one canonical deep-link
  target when no-JavaScript navigation matters?

A successful ReScript and production build cannot answer these runtime questions.

## Report the verdict

State where ReScript earned its cost and where it did not. A hybrid is often the strongest result:
framework-native TypeScript for ecosystem adapters, ReScript for validated data and protocol or
state logic, and static framework templates where no compiler-owned domain behavior exists.

Answer greenfield language choice, value of the completed migration, and default advice for
future maintenance separately. A comprehensive rewrite can be worthwhile as an experiment while
still showing that language-complete migration is a poor production default.

Call the result positive only when compiler-guided prevention and stronger domain ownership
outweigh setup, bindings, adapters, and migration risks for the actual project. Record residual
risks and the next change most likely to test the claimed long-term payoff.
