# T3 Code

This session runs in a T3 Code thread, so the `t3-code` MCP tools are available.

- Use a T3 subagent (`delegate_task`) for short agent work on any model, such as a lookup, review, quick edit, or check, so the work shows under this thread. Give phases, experiments, and long work (expected to run or queue for over 1 hour) to a child thread: `homebased t3 launch --child --project <path> --message-file <brief>`, which reports back here once and is then settled. Never launch one with `t3_thread_launch`, which records no link to this thread. Keep `homebased` tasks for command workloads, Fleet machines, the GPU queue, and `after` chains.
- To wait on homebased tasks or GPU queue jobs, run `homebased wait --next <id> [<id> ...]` as a background Bash command with `timeout: 7200000` right after submitting, with task and job ids alike, pass its task id to `t3_background_wait`, and end the turn, so T3 lists the thread under Waiting. It exits after the next events and wakes the thread once; read its output, then start it again with the ids whose final event you have not seen. With no event it exits after 55 minutes, so each wake-up lands inside the hour-long prompt cache, and prints on stderr the command that starts it again; run that. Do not use a `Monitor` for this: it expires after 30 minutes and wakes the thread each time with nothing to report.
- For long work, sleep instead: run `homebased wait --long <id> [<id> ...]` as an ordinary Bash command, not in the background and with no `t3_background_wait`, and end the turn. It exits at once, and the thread then wakes only on each target's final event, which lists the progress events held meanwhile under `held_events`, or on an alert, after which the hold stays and no new wait is needed. It does not compact the thread; the daemon compacts a sleeping thread while it is idle. A T3 subagent does no long work: there `--long` cannot sleep and only waits up to 115 minutes.
- For a process you start and do not wait on, such as a dev server, proxy, or emulator, run `homebased service start --name <name> --port <port> -- <command>` (or `--ready-line <regex>`) instead of background Bash: it returns once the service is ready, stops when this thread settles, and reports if it dies. `homebased service stop <id>` ends it sooner.
